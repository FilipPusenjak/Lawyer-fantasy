# Lawyer Fantasy — architecture

A fantasy-football-style league for a high school mock trial club. Teams draft
real lawyers and law firms and score points from events in their public court
cases. Phase 1 is fully playable with manually entered data; Phase 2 adds
CourtListener; Phase 3 adds AI-suggested events (always commissioner-approved).

## Stack

- Next.js 16 App Router + React 19 + TypeScript. **Cache Components is OFF**
  (`next.config.ts`), so pages that read cookies/DB are dynamic automatically.
  Route props: `PageProps<"/leagues/[leagueId]/team">`, `LayoutProps<…>`,
  `RouteContext<…>` (global helpers generated by `next typegen`). `params` and
  `searchParams` are Promises. The Next docs for this exact version are in
  `node_modules/next/dist/docs/` — check them before using an unfamiliar API.
- Tailwind CSS v4 with design tokens in `src/app/globals.css` (`bg-surface`,
  `text-muted`, `border-line`, `bg-brand`, `text-brand-ink`, `bg-brand-soft`,
  `text-accent`, `text-pos`, `text-neg`, `bg-warn-soft`…). Visual style is
  "Game night": dark only, electric-lime brand color, Oswald condensed
  headings/buttons/scores (`font-display`), Inter body text. Always use the
  tokens, never raw colors, so the theme stays consistent.
- Postgres on Neon via Drizzle ORM (`src/db/schema.ts`, `src/db/index.ts`),
  `@neondatabase/serverless` Pool (supports transactions and `FOR UPDATE`).
- Vitest for pure logic (`tests/unit`), Playwright for e2e (`tests/e2e`).

## Domain model

- **Users** sign up with username + password (email optional). Sessions are DB
  rows; cookie `lf_session`. Site admins (`users.is_admin`, granted with `npm run make-admin -- <username>`)
  are the only ones who can **create leagues**. Anyone with an account can join a
  league with its invite code.
- **Pools** hold the "legal world": `lawyers` (kind `lawyer` or `firm`, one
  fixed `position`), `cases`, `case_appearances` (lawyer ↔ case, side
  `plaintiff`/`defendant`), and `scoring_events`. A league uses one pool; the
  demo pool is separate from the real one. Commissioners of any league using a
  pool (and admins) can manage it (`canManagePool`).
- **Scoring events** are facts: a type (see `EVENT_TYPES` in
  `src/lib/settings.ts`), a date (`occurred_on` → week), and either a
  case+side (credits every lawyer on that side) or a specific lawyer (e.g.
  sanctions, Supreme Court argument). Points only count once `status =
  'approved'`. Values come from each league's scoring settings, so editing values
  re-scores open weeks. Firms get `firmMultiplier` × each event once.
  `filing` events are capped per lawyer per week. Engine: `src/lib/scoring.ts`.
- **Leagues** have JSON `settings` (`LeagueSettings`, zod-validated, see
  `src/lib/settings.ts`), `season_start` (a Monday), status
  `setup → drafting → in_season → playoffs → complete`.
- **Weeks** are Mon–Sun in the league time zone; week N's lineups lock at
  `lockTime` on its Monday (`src/lib/time.ts`). Matchups span
  `matchupWeeks` weeks (default 2); team score for a matchup = sum of weekly
  starter totals.
- **Lineups**: one row per (team, week) with `starters` (array aligned with
  `starterSlots(settings.roster)`); the effective lineup for week N is the row
  with the largest week ≤ N. Only write rows for weeks that are not locked
  (`editableWeek`). See `src/server/services/lineups.ts`.
- **Rosters**: `roster_spots` (unique per league+lawyer). Use
  `addLawyerToTeam` / `removeLawyerFromTeam` in `src/server/services/roster.ts`
  (they handle waiver holds and clearing upcoming lineups).
- **Waivers**: rolling priority (`teams.waiver_priority`, 1 = first), processed
  weekly at `leagues.next_waiver_run_at`. Dropped and undrafted lawyers sit in
  `waiver_holds` until the next run; everyone else unrostered is a free agent.
  Pure algorithm in `src/lib/waivers.ts`.
- **Trades**: proposed → accepted (commissioner review window,
  `settings.trades.reviewHours`) → completed, or rejected/cancelled/vetoed/failed.
- **Draft**: snake (`src/lib/draft.ts`), clients poll every ~2 s; the server
  auto-picks lazily when the deadline has passed.
- **Results** (`src/server/services/results.ts`): commissioners "finalize"
  weeks in order, which snapshots scores (`snapshotWeek`). A matchup is final
  when all its weeks are finalized (median games use the median of all teams'
  totals). Finalizing the last regular-season week seeds the playoffs
  automatically (top `playoffTeams` from standings, byes for top seeds); each
  settled round creates the next; one winner left → status `complete`. Only the
  latest finalized week can be reopened; reopening deletes any playoff round
  that finalizing it created (such a round has no finalized weeks yet), and it
  is rebuilt with fresh seeding when re-finalized. `finalizeEndedWeeks`
  finalizes every ended week in order (used by the seed). When the season completes, open trades are
  failed ("season ended") and pending waiver claims are marked lost.
- **Cron**: `vercel.json` schedules `/api/cron/daily` once a day at 09:17 UTC
  (Vercel Hobby limit). It needs `CRON_SECRET` set in Vercel (401 otherwise)
  and returns 500 if any league's maintenance throws. League pages also run
  maintenance lazily on every view.

## Code layout & conventions

- `src/lib/*` — pure, framework-free logic (unit tested). Safe on client.
- `src/server/services/*` — DB services. **No `server-only`, no cookies** so the
  seed script can import them. Accept `db: DbOrTx` so they compose in
  transactions.
- `src/server/league-context.ts` — request auth: `getLeagueContext(leagueId)`
  (Server Components; 404s non-members), `getCommissionerContext`,
  `actionLeagueContext(leagueId, { commissioner })` (Server Actions; throws
  `UserError`), `canManagePool`.
- `src/server/auth/*` — sessions/passwords. `requireUser()` redirects to /login.
- Server Actions live in an `actions.ts` next to the route, start with
  `"use server"`, **re-verify auth inside every action**, validate input with
  zod, wrap the body in `runAction(...)`, return `ActionResult`
  (`src/server/action-result.ts`), and call `revalidatePath` after mutating.
  Throw `new UserError("message")` for user-facing errors.
- Use `db.transaction(async (tx) => …)` for multi-step mutations.
- UI: `src/components/ui.tsx` (server-safe kit: `Page`, `PageHeader`, `Card`,
  `Button`, `LinkButton`, `Badge`, `Notice`, `Field`, `Input`, `Select`,
  `Points`, `ListRow`, `Tabs`, `EmptyState`) and `src/components/ui-client.tsx`
  (`SubmitButton`, `ActionForm`, `ActionMessage`). Mobile-first: everything
  fits a 375 px screen, tap targets ≥ 44 px, `Page` gives a max-w-xl column with
  room for the bottom nav.
- League pages live under `src/app/leagues/[leagueId]/…`; the layout provides
  the header, bottom nav (`src/components/league-nav.tsx`) and runs lazy
  maintenance (`src/server/services/maintenance.ts`).
- **Neutral language**: show case facts neutrally (caption, court, docket
  number, event type, date, source link). No commentary about lawyers.

## Projections and rankings

- `src/lib/projections.ts` (`projectPool`) projects every lawyer and firm per
  week: their own recent history blended with a prior. For cases with a
  researched outlook (`cases.outlook`, `src/lib/outlook.ts`) the prior uses the
  case's real docket activity (switching to a post-event pace after a milestone
  with `activityAfter`, e.g. a verdict), and scheduled/likely events
  (arguments, trials, decisions, pleas…) are added in the weeks they could
  happen. Timing conditions only on complete weeks and only on what an approved
  event would have shown (a sentencing leaves no event); a terminal event stops
  the case's activity. `resolveMilestones` ties each approved event after the
  research date to the one milestone that could have produced it (same type and
  side or lawyer; routine rulings only inside the window), preferring a
  non-terminal explanation, so a co-defendant's plea doesn't end the case. Events
  that resolved a milestone stay out of own-history rates, and a case that ends
  before a later terminal stage (a plea before trial) drops that stage's
  follow-on milestones. On researched cases, own history counts only recurring
  activity (filings, rulings), so a one-off verdict isn't projected weekly. The
  weekly range mixes the target week's scheduled outcomes into the base range.
  Cases without an outlook use typical rates per case type.
- Firms are matched by `firmKey` (`src/lib/firms.ts`) on import, so two
  spellings of one firm never become two firms.
- Season rank (`overallRank`) = projected points over the rest of the season;
  draft ranks follow it ("Use projection ranks"). Week rank = this week's
  projection. The Rankings page opens on season points before the season and on
  the week afterwards; the rank shown always matches the sort.
- Outlook data and research notes: `data/real-pool-2026-27/`, imported with
  `scripts/import-outlooks.ts`. The UI shows only each case's factual status
  line, never outcome probabilities.

## Court data and Claude suggestions

- `src/server/services/court-sync.ts` runs the daily sync (cron) and the
  commissioner's "Sync now". Pure planning (windows, cursors, caps) lives in
  `src/lib/court/sync-plan.ts`; keyword rules in `src/lib/court/classify.ts`
  (CourtListener) and `src/lib/court/scotus.ts` (Supreme Court feed).
- Phase 3: `src/server/court/ai-classify.ts` sends a case's candidate
  CourtListener entries (up to 25) to Claude Opus 5.5 with the official
  `@anthropic-ai/sdk` (`beta.messages.parse`, `output_config: { effort: "low",
  format }`, cached system prompt, `fallbacks: "default"`). Its verdicts replace
  the keyword rules for the entries it answers; anything else (no key, budget
  or time used up, refusal, error) falls back to the keyword rules.
- Every automatic suggestion stores why it was suggested in
  `scoring_events.suggestion_note`; Claude's also store
  `suggestion_confidence` and `suggestion_model`. The review queue shows them
  ("Sorted by Claude"). Suggestions are always pending until approved.
